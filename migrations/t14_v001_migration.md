# T14 v001: additive historical observation schema — synthetic-only

No existing database may be migrated by this task. There is no startup hook,
automatic migration runner, ALTER of core tables or data backfill. The initializer
creates a new uniquely named disposable SQLite database, including the existing
core schema and a tiny synthetic catalog, only after explicit acknowledgment.
It cannot adopt/overwrite an existing file. This is not T15 stock/PO/sales simulation.

Artifacts: `t14_v001_expand_sqlite.sql` and `t14_v001_expand_mysql.sql` add
historical_demo_target, import_runs, historical_datasets, sales_observations and
import_quarantine, constraints/indexes, six immutable/staging-only triggers and
published_sales_observations view. They reference existing branches/skus by FK.
The separate metadata in `ingestion/schema.py` leaves T04–T12 frozen schemas and
application models unchanged. `scripts/render_t14_schema.py` only writes DDL files.

ImportRun binds a unique manifest hash and unique(source, revision), canonical
configuration/checksums, durable input line/byte checkpoint, counters/reconciliation,
base publication ID and UTC timestamps. The active-run pointer is a FK. Facts also
bind run/source/revision via composite FK and branch/SKU IDs via FKs. Daily natural
keys are unique per revision. Unknown coverage is null units, distinct from observed
zero; nullable USD weekly price metadata never becomes POS/MYR revenue.

The SQLite artifact is rehearsed exactly on a fresh in-memory core schema, preserving
a sentinel legacy product and enforcing FKs. MySQL DDL is offline only (InnoDB,
binary collation, FK/CHECK/trigger/view syntax); no MySQL execution, isolation,
locking, implicit-commit or restore evidence exists. Runtime accepts **SQLite only**.
Live disposable MySQL and any future runtime port need separate approval/testing.

## Future real-data cutover remains forbidden

Before any different target/mode, obtain rights/accepted terms and intended-use
approval, separately authorized source fingerprints, dedicated demo target approval,
verified backup/restore and exact schema/checksum review. Record any later approved
migration in the project's registry with actual application evidence. Merely applying
this artifact cannot satisfy the application ID/token capability or unlock M5.
No SchemaMigration row falsely claiming existing-target cutover is created here.

## Restart and rollback

Restart the exact generated manifest against the same attested target. Chunks commit
facts/quarantine/checkpoint/counters together. A failed chunk rolls back; the prior
checkpoint survives. Changed bytes/configuration fail validation; fix corruption by
restoring exact generated bytes, never by editing stored hashes or checkpoints.

Staged/reconciled revisions remain invisible until atomic publication. If publication
fails, old status/pointer remain unchanged. Retry the same run after resolving the
cause. A replacement based on an older active revision is rejected; generate a new
synthetic revision after the winning publication rather than editing its base ID.
Superseded replays do not re-activate old history.

Retain immutable old facts and quarantine evidence. There is no destructive down
migration, delete/reset command or automatic repoint to old data. Preserve a failed
demo for investigation or create a separately named fresh demo target. Any manual
cleanup/removal is outside the importer; never aim cleanup at an operational DB.
